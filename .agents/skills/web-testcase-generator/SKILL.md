# Web Test Case Generator Skill

Skill นี้ใช้สำหรับเข้าไปสำรวจระบบ/หน้าเว็บจริง แล้วสกัดข้อมูลฟิลด์ เงื่อนไข Validation และ Flow การทำงาน เพื่อเขียน **Test Case ภาษาไทย** ในรูปแบบมาตรฐานสำหรับ QA / Tester

> ⚠️ **สำคัญ:** ทำเฉพาะ scope / ฟังก์ชันที่ผู้ใช้สั่งเท่านั้น ห้ามทำ scope อื่นนอกเหนือจากที่ระบุ

## 1. การเตรียมข้อมูลและ Login เข้าสู่ระบบ

### บัญชีผู้ใช้งานสำหรับการทดสอบ (Test Accounts)

| Username | Password | บทบาท (Role) | ขอบเขตข้อมูล (Scope) |
|---|---|---|---|
| `council.admin` | `11111111` | ผู้ดูแลระบบสภา (Central Admin) | ทั้งประเทศ (ทุกจังหวัด) |
| `council.executive` | `11111111` | ผู้บริหารสภา (Executive) | ทั้งประเทศ (ทุกจังหวัด) |
| `burapha.admin` | `11111111` | ผู้ดูแลระบบโรงเรียน (School Admin) | โรงเรียนบูรพา |
| `burapha.director` | `11111111` | ผู้อำนวยการ (Director) | โรงเรียนบูรพา |

1. อ่านค่าจากไฟล์ `.env` หรือตารางบัญชีทดสอบด้านบน:
   - `BASE_URL`: URL ของระบบ (เช่น `https://sts-frontend-gold.vercel.app`)
   - `USERNAME` และ `PASSWORD`: บัญชีที่ตรงตามบทบาทและ scope ที่ต้องการทดสอบ
2. เปิด Browser เข้าไปยัง `BASE_URL` และทำการ Login ด้วย Username/Password ที่ระบุ
3. นำทางไปยังเมนูหรือหน้าจอที่ต้องการทดสอบ

## 2. การสำรวจหน้าจอและเงื่อนไข (Exploration)

เมื่อเข้าสู่หน้าจอเป้าหมายแล้ว ให้ตรวจสอบองค์ประกอบต่อไปนี้:
- **เมนูและปุ่ม:** เช่น เมนู "ข้อมูลพื้นฐาน", ปุ่ม "เพิ่มรายการ", ปุ่ม "แก้ไข", ปุ่ม "ลบ", ปุ่ม "บันทึก"
- **ฟิลด์ข้อมูลใน Form:** เช่น รหัส, ชื่อภาษาไทย, ชื่อภาษาอังกฤษ, ลำดับแสดงผล, สถานะ
- **เงื่อนไข Validation / Error Message:**
  - เงื่อนไข Required (ไม่ได้กรอกข้อมูล)
  - รูปแบบตัวอักษร (เช่น ภาษาไทย, ภาษาอังกฤษ, ตัวเลข, สัญลักษณ์พิเศษ, ขีดล่าง `_`)
  - ความยาวตัวอักษร (Min / Max length)
  - ข้อความแจ้งเตือนข้อผิดพลาด (Error / Warning message) ที่แสดงบนหน้าจอจริง

## 3. รูปแบบ Test Case มาตรฐาน (Template)

ทุก Test Case ที่สร้างขึ้น **ต้องใช้โครงสร้างและลำดับตามฟอร์มนี้เท่านั้น**:

```text
### TC-<รหัส>: <หัวข้อ Test Case>

- **TC ID:** TC-<รหัส>
- **TC Description:** <คำอธิบายการทดสอบ เช่น ตรวจสอบการกรอกข้อมูลเพิ่มรายการ "..." ด้วยรหัสที่ผิดพลาด>
- **Test Step:**
  1. เข้าสู่หน้า "<ชื่อเมนู/หน้าจอ>"
  2. เลือกประเภทของข้อมูลพื้นฐานเป็น "<ชื่อประเภท>"
  3. คลิกปุ่ม "<ชื่อปุ่ม>"
  4. กรอกช่อง <ชื่อฟิลด์> "<ค่าที่กรอก>"
  5. กรอกช่อง <ชื่อฟิลด์> "<ค่าที่กรอก>"
  6. กรอกช่อง <ชื่อฟิลด์> "<ค่าที่กรอก>"
  7. กดปุ่ม "<ชื่อปุ่มบันทึก/ยืนยัน>"
- **Expected:** <ผลลัพธ์ที่คาดหวัง เช่น แสดงข้อความแจ้งเตือน "..." หรือ บันทึกข้อมูลสำเร็จและแสดงในตาราง>
- **Test Data:**
  1. "<ข้อมูลที่ใช้ในแต่ละขั้นตอน>"
  2. "<ข้อมูลที่ใช้ในแต่ละขั้นตอน>"
  3. "<ข้อมูลที่ใช้ในแต่ละขั้นตอน>"
```

> ⚠️ **ลำดับที่ต้องเรียงเสมอ:** `### TC` → `TC ID` → `TC Description` → `Test Step` → `Expected` → `Test Data`

## 4. หลักการออกแบบและแบ่ง Screen (Screen Structure Strategy: Global vs Role-Specific)

เมื่อฟังก์ชันใดฟังก์ชันหนึ่ง (`FN-STS-XX`) รองรับการเข้าถึงจาก **หลายบทบาท (Multi-Role)** ให้แบ่ง Screen ออกเป็น 2 ระดับเสมอ เพื่อป้องกันความซ้ำซ้อนและแยกแยะสิทธิ์ได้อย่างชัดเจน:

### 1. Global / Common Screen (`SC-STS-XX-01`)
> **นิยาม:** หน้าจอรวมสำหรับการทดสอบพฤติกรรมพื้นฐานที่ **ทุก Role ได้รับผลลัพธ์เหมือนกันทั้งหมด** หรือไม่ขึ้นกับบทบาทผู้ใช้งาน

* **สิ่งที่ต้องเขียนใน Global Screen (`SC-STS-XX-01`):**
  - **Validation & Form Constraints:** เช็กการกรอกข้อมูล Required, รูปแบบตัวอักษร (ไทย/อังกฤษ/ตัวเลข/สัญลักษณ์), ความยาวสูงสุด (Max Length), Duplicate Data
  - **ข้อความแจ้งเตือนกลาง:** Error / Warning message ทั่วไป (เช่น "กรุณากรอกชื่อผู้ใช้งาน", "ชื่อผู้ใช้งานหรือรหัสผ่านไม่ถูกต้อง")
  - **UI / Display ทั่วไป:** Placeholder, ภาษาไทยบนปุ่ม, การแสดงผลตาราง/Pagination พื้นฐาน

### 2. Role-Specific Screens (`SC-STS-XX-02`, `SC-STS-XX-03`, ...)
> **นิยาม:** หน้าจอที่แยกเฉพาะตาม **บทบาท (Role) และสิทธิ์การเข้าถึง (Permission / Scope)** ที่มีผลลัพธ์แตกต่างกัน

* **สิ่งที่ต้องเขียนใน Role-Specific Screen:**
  - **สิทธิ์การมองเห็นเมนู (Sidebar Menu):** เมนูที่แสดง / ซ่อน ตามสิทธิ์ของ Role นั้นๆ
  - **ขอบเขตข้อมูล (Scope Filter):** เช่น ระดับสภา = `"ขอบเขต ทุกจังหวัด"`, ระดับโรงเรียน = `"ขอบเขต โรงเรียน..."`
  - **การแสดงผลแดชบอร์ด/วิดเจ็ต:** KPI การ์ด, กราฟ, แผนที่ความเสี่ยงที่แสดงผลเฉพาะระดับ
  - **ปุ่ม Action เฉพาะสิทธิ์:** เช่น ปุ่ม เพิ่ม/แก้ไข/ลบ (เฉพาะ Admin), ปุ่ม ดูข้อมูล/ส่งออก (Executive/Director)
  - **เมนูโปรไฟล์ (Dropdown Profile):** ตรวจสอบชื่อผู้ใช้, สังกัด, และตำแหน่งของแต่ละบทบาท

## 5. โครงสร้าง Test Scenario (TS) หลัก

ภายใต้แต่ละ Screen ให้จัดกลุ่ม Test Cases ด้วย **3 Test Scenario หลัก** เสมอ:

| Test Scenario ID | ชื่อ Test Scenario | คำอธิบาย |
|---|---|---|
| **TS-STS-XX-01** | ตรวจสอบการกรอกข้อมูล | ทดสอบการกรอกฟิลด์ทุกช่อง ทั้ง Positive และ Negative (Validation, Format, Length) |
| **TS-STS-XX-02** | ตรวจสอบการทำงานของปุ่ม | ทดสอบปุ่มทุกปุ่มในหน้าจอ เช่น เข้าสู่ระบบ, เพิ่มรายการ, บันทึก, ยกเลิก, แก้ไข, ลบ |
| **TS-STS-XX-03** | ตรวจสอบการแสดงผล | ทดสอบการแสดงผล Sidebar, Scope, การ์ด KPI, วิดเจ็ต, ตาราง, และ Dropdown โปรไฟล์ |

> 📌 **กฎการตั้งรหัส Test Case ID (TC ID):**
> - รหัส TC ต้องสอดคล้องกับ TS เสมอ เช่น ภายใต้ TS-02 (ปุ่ม) ต้องเป็น `TC-STS-XX-02-YY` และภายใต้ TS-03 (แสดงผล) ต้องเป็น `TC-STS-XX-03-YY`

> 🎯 **เกณฑ์จำนวน Test Cases ขั้นต่ำ (15+ Test Cases Rule):**
> - **ทุกฟังก์ชัน (`FN-STS-XX`) จะต้องมีจำนวน Test Cases ไม่น้อยกว่า 15+ Test Cases (15 - 25 TCs)** เพื่อให้ครอบคลุมการทำงานทุกมิติ:
>   1. **TS-01 (Inputs & Filters):** 5-8 TCs (Positive, Negative, Required, Format, Boundary, Duplicate, Filter, Search)
>   2. **TS-02 (Buttons & Actions):** 5-8 TCs (ทุกปุ่ม, การเปิด/ปิด Modal, Confirm, Cancel, Action ผลการทำงาน)
>   3. **TS-03 (Display & Permissions):** 5-8 TCs (UI Display, Dashboard, Timeline, Badges, Table Data, Scope & Role Permissions)

## 6. รายละเอียดแต่ละ Test Scenario

### TS-STS-XX-01: ตรวจสอบการกรอกข้อมูล
ครอบคลุม Test Cases ต่อไปนี้:
- **Positive:** กรอกข้อมูลถูกต้องครบถ้วน → บันทึกสำเร็จ
- **Negative - Format ผิด:** รหัสมีอักขระพิเศษ, เว้นวรรค, ภาษาไทย, ขึ้นต้นด้วยตัวเลข
- **Negative - Required:** ไม่กรอกฟิลด์ที่จำเป็น (ว่าง)
- **Negative - Duplicate:** กรอกรหัสซ้ำกับที่มีอยู่ในระบบ
- **Negative - Boundary:** กรอกเกินจำนวนตัวอักษรสูงสุด, ลำดับแสดงผลเป็นค่าติดลบ/ตัวอักษร

### TS-STS-XX-02: ตรวจสอบการทำงานของปุ่ม
ครอบคลุม Test Cases ต่อไปนี้:
- ปุ่ม "เพิ่มรายการ" → เปิด Modal ฟอร์ม
- ปุ่ม "บันทึก" → บันทึกข้อมูล
- ปุ่ม "ยกเลิก" → ปิด Modal โดยไม่บันทึก
- ปุ่ม "แก้ไข" → เปิด Modal แก้ไข
- ปุ่ม "ปิด" / "เปิด" → เปลี่ยนสถานะใช้งาน
- ปุ่ม "ลบ" → ลบรายการ (ถ้ามี)
- ปุ่ม "ยืนยัน" / "ยกเลิก" บน Dialog

### TS-STS-XX-03: ตรวจสอบการแสดงผล
ครอบคลุม Test Cases ต่อไปนี้:
- เข้าถึงหน้าจอสำเร็จ แสดงองค์ประกอบครบ
- Dropdown แสดงรายการครบถ้วน
- ตารางแสดงข้อมูลถูกต้องตามประเภทที่เลือก
- คอลัมน์ตารางแสดงครบ (ลำดับ, รหัส, ชื่อ, สถานะ ฯลฯ)
- สถานะแสดงผลถูกต้อง (เปิดใช้งาน/ปิดใช้งาน)
- ข้อความแจ้งเตือน/Error แสดงถูกต้อง

## 8. รูปแบบไฟล์ HTML (Interactive Excel Hierarchy Table)

ไฟล์ `.html` ที่สร้างในแต่ละฟังก์ชันต้องมีองค์ประกอบดังต่อไปนี้:

   - การ์ดสรุปขอบเขตบทบาทผู้ใช้งาน (Target Roles)

## 🔁 Workflow การ Extract, Sync เอกสาร และแก้ไข Playwright Spec Files

ทุกครั้งที่ผู้ใช้งานสั่งให้สกัด (extract) ข้อมูลจาก HTML แล้วนำไปอัปเดตฟังก์ชัน ให้ทำตาม 4 ขั้นตอนนี้เสมอ:

1. **Extract & Backup ข้อมูล:**
   - สกัด Test Case ID, Description, Test Step (1, 2, 3...), Expected Result, Test Data
   - บันทึกไฟล์ JSON (`extracted_testcases.json`) และ CSV (`extracted_testcases.csv`)
2. **Update Markdown Documentation (`.md`):**
   - อัปเดตไฟล์ `testcases/FN-STS-XX_<ชื่อฟังก์ชัน>/FN-STS-XX_<ชื่อฟังก์ชัน>.md` ให้ข้อมูลและ Test Steps ตรงตามที่ extract มา 100%
3. **Align Playwright Automated Spec Files (`.spec.ts`):**
   - อัปเดตไฟล์ `TS-STS-XX-01.spec.ts`, `TS-STS-XX-02.spec.ts`, `TS-STS-XX-03.spec.ts`
   - ยึด **Test Step** (เรียงตามลำดับข้อ 1, 2, 3...) และ **Expected Result** เป็นหลักสำคัญสูงสุด ไม่ฝืนแก้สเปกเพื่อทำให้ผ่าน
   - เรียกใช้ `loginWithSession(page, user, pass)` เพื่อดึง Session เดิมจาก `.auth/<user>.json` ป้องกัน Rate Limit
   - ตัดการย้ายหน้าไป `/profile` ที่ไม่จำเป็นออก เพื่อเริ่มทดสอบจากหน้าหลัง Login ทันที
4. **User Reporting & Handover:**
   - เมื่ออัปเดตไฟล์เสร็จเรียบร้อย **ไม่ต้องสั่งรัน Playwright อัตโนมัติเอง** (เพื่อป้องกัน Rate Limit)
   - สรุปรายการไฟล์และตัวอย่างคำสั่งรันให้ผู้ใช้งานนำไปสั่งรันทดสอบด้วยตนเอง
